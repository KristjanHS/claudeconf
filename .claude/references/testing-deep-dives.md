# Testing — deep dives

Pulled from `~/.claude/rules/testing.md` when you hit one of: the falsifying-regime family (regression /
property / "duplicate" / cross-port parity), slow suites / fixtures, `mock.patch` import cost, external-tool
skip guards, bystander assertions for pruning/filter tests, time-dependent expected values, or `.bats`
quirks. The rule keeps the value gate; the mechanisms live here.

## The falsifying-regime family (value-gate check 3, four ways)

All four say one thing: **a green assertion proves nothing until you have confirmed its fixture reaches the regime where the code would be wrong.** The rule keeps the one-liners; the mechanisms are here.

**Regression test — must fail against the OLD code.** When you add a test alongside a fix/refactor that removes a heuristic, arrange its inputs so the *old* implementation produces the wrong answer — otherwise it passes against both versions and guards nothing. Reason through (or temporarily run) the old code path on your fixture: if both old and new pass, the data arrangement doesn't trigger the bug (e.g. a cap/limit only starves under a specific ordering — put the stressor where the order actually reaches it). A green regression test proves nothing until you've confirmed it would go red on the code you just deleted.

**Property test — only as strong as the regime its fixtures sample.** When asserting an invariant over generated/enumerated inputs, name the regime that would BREAK it and put a fixture there. Many natural fixture shapes sit entirely inside the region where the property holds trivially, so the suite goes green on a false invariant: a monotone ramp, a sorted input, a single-element collection, a happy-path sequence with no adjacent transitions. Add a vacuity guard too — assert the fixtures actually exercise the behavior (some input changes the output), or a pinned-constant fixture will pass forever.

**"Duplicate" test — check whether the survivor is circular.** An assertion whose expected value is a fixture *generated by the function under test* pins wiring, not behavior — it cannot fail on a formula change. So the hand-kept literal that looks like a stale copy is often the only real anchor, and "collapse the duplicate" turns the suite into `expect(fixture).toEqual(fixture)`. Trace each expected value to its origin (hand-computed? another implementation? emitted by the subject?) before removing either. This applies to a cleanup instruction *you wrote yourself* a session ago — verify its premise, don't execute it on trust.

**"Two sources must agree" — count the sources the test actually reads.** A drift pin whose stated job is "module A's constant matches module B's" is worthless if it compares A's value to a literal **re-stated in the test file**: that literal is a *third* source, so the assertion can never observe A and B disagreeing, and it goes green while they drift. Read the test's own imports and ask which of the two named sources it never touches. Worked example (private-app 2026-07-18): `families.ts` defined `rungCut(r) = (r−1)/8` while `t1dial.ts` computed `dangerScore = (rung−1)/8` with its own literal; the "cross-module pin" looped `expect(rungCut(r)).toBeCloseTo((r−1)/8)` — pure restatement, blind to `t1dial.ts` entirely — and the `families.ts` docblock advertised it as pinning the two against each other. Two follow-ons: (1) the honest fix is usually to **dissolve the class by single-sourcing** (make B derive through A) rather than keep asserting agreement between duplicates — then the surviving test pins *wiring* and should say so; ship a class falsifier for the duplicate (`grep -rn -- '- 1) / 8' src/` → exactly one hit) and run it file-wide. (2) Where the values are exactly representable, assert with `toBe`, not `toBeCloseTo` — a tolerance admits precisely the sub-ULP drift such a design usually exists to forbid.

**Cross-port parity — only as strong as its comparator.** If it asserts equal length (or equal keys) before comparing elementwise, it is blind to every divergence in *shape* — one port dropping a bad row where the other emits null-in-place, say. Green then means "the fixture never entered the divergent regime", not "the ports agree". Put a fixture in that regime, or the parity claim is true-by-input rather than true-by-construction.

## Reconstructing derived (not persisted) state — replay depth must cover the state's lifetime

Rebuilding a derived-not-persisted value (a latch, a hold, a hysteresis band) by peeking ONE step back gives
one-step memory, not the real state. A value that fires and then HOLDS for N closes before releasing needs the
replay to walk its full *maximum lifetime*, not just the last transition — and a damping-WIDTH constant sizes
the smoothing, never the DURATION, so it can't stand in for how long the state persists. The proving fixture
must span the whole fire→hold→release arc: a fixture that only reaches fire→next-step confirms one-step memory
and passes green while multi-step hysteresis is silently broken.

## Reducing test runtime

When a suite is slow, prefer deleting low-value tests (apply the 5-check gate) over hiding them behind markers
(`@pytest.mark.slow` + default-exclude). Marker splits hide cost; they don't reduce it, and low-signal tests
stay on the CI bill. Also look for unshared fixtures — multiple tests running the same expensive setup
(subprocess calls, recalc, fixture rebuilds) are the usual hot spots. `pytest --durations=25` exposes them.

**In a JS/TS suite, measure COLLECTION before you touch assertions.** A per-file-isolated runner re-imports
the same barrels once per test file, so a suite's cost is often module *collection*, not the tests: measured
once at 51s of ~93s CPU, with assertions only 25s and an empty test file still costing ~12ms. The instinct to
delete tests aims at the smaller half — check the split first (`vitest --reporter=verbose`, or time an empty
file) before proposing any deletion.

**A runner's parallelism knobs may only be honoured at ROOT scope.** Options like `pool` / `isolate` /
`fileParallelism` can be accepted by the type system inside a sub-project/workspace entry and silently
ignored — the failure mode of a scope mismatch is silence, not an error. Assert on a *consequence* (wall-clock
delta, worker count, two files provably not overlapping), never on the key's presence in the config; and
triage what the option was protecting, since the same key is often both a speed knob and a safety guard.

Session/module fixtures that mutate a file (recalc, rebuild, seed) must return the mutated artifact (path or
loaded workbook), not just metadata. If the fixture returns only stats/JSON, every downstream caller that
needs to read the mutated file has to re-do the work — duplicating the expensive setup the fixture was meant
to amortize.

When migrating a module fixture to a session fixture, verify via full-suite wall-clock delta (not
`--durations` top-N). `pytest --durations=N` attributes session-fixture setup cost to the *first* test in the
run that triggers the chain — alphabetical ordering often keeps the migrated test at the top of durations even
though total runtime dropped. In-isolation (`pytest tests/<file>.py`) runs show zero savings because the
session fixture still builds from scratch; savings only materialize when a sibling consumer already triggered
the chain.

**External-process tests go in a manual tier from day one.** Tests that `docker exec`, `kubectl`, `devc exec`,
drive a headless browser, or hit a real network service carry seconds of per-test overhead even when the
skip-guard fires — the readiness probe itself is expensive. Gate them behind an opt-in target
(`tests/manual/*.bats`, `pytest -m e2e`, `make test-e2e`) and keep them out of the default suite + pre-push. A
skip-clean test that adds 5s × N tests to every default run trains users to `--no-verify`. Move at the commit
that adds the test, not after someone complains.

**Debug slow suites by per-file timing, not output-channel intuition.** When a suite regresses from fast to
slow, time each file individually (`for f in tests/*.bats; do time bats "$f"; done` or
`pytest --durations=0 tests/<file>`) to find the hot spot before hypothesizing about buffering/output
filtering. Output buffers (awk collapsing TAP lines, pytest `-q`) make a slow run *look* hung but don't cause
the slowness — fixing the display without fixing the timing papers over the symptom.

**`unittest.mock.patch("heavy.module.attr", ...)` triggers the real import of `heavy.module`.** Even though
the patch then replaces `attr` with a fake, the dotted-path resolver imports the parent to *find* the
attribute. For modules whose import is multi-second (`pyannote.audio`, `torch.distributed`, `transformers`,
`tensorflow.keras`, …), this pays the full import cost in a test that never exercises the real code.

**Symptom:** `--durations` shows one outlier test in the family at N seconds and the rest at <0.01s. The
outlier is whichever test ran first — subsequent tests get the cached import for free. Looks asymmetric; isn't.

**Confirm:** time the import standalone
(`python -c "import time; t=time.perf_counter(); from heavy.module import attr; print(time.perf_counter()-t)"`).
If it matches the slow test's duration, the patch is the cause.

**Fix:** drop the patch (`rules/testing.md` bans monkeypatch/mock.patch). Inject the heavy callable as a
parameter, or extract the logic around it into a pure function, and test that without importing `heavy.module`.

## External tool skip guards

When a test skips on a missing binary, canary-test the tool on trivial input (`echo '{}' | yq .`) rather than
relying on `command -v` alone. A corrupted snap/apt install can present as installed but fail on every real
call — `command -v` returns 0, the assertion under test fails, and you get a false negative instead of a clean
skip.

## Before deleting on coverage grounds

Deleting a unit test on "integration covers it" grounds requires grepping the cited integration caller to
verify it exercises the same code branches (input shape, formula form, edge cases) — prod paths often differ
from test paths. "Covered elsewhere" without a grep is the strongest predictor of a silent coverage drop.

## Pruning / removal tests need a bystander

When testing code that removes or filters items ("orphan pruning", "remove stale entries", "drop unknown
keys"), the test MUST include at least one item that is NOT supposed to be removed and assert it survives with
value intact. A target-only assertion (`assert target not in result`) passes even if the pruning loop drops
every item — the test proves nothing about selectivity. The bystander assertion is the real correctness gate.

For regex/pattern-filter tests specifically, the bystander must be an *adjacent-but-non-matching* input — one
that shares substrings with a positive case so a broken anchor or `\b` boundary surfaces. `"please run the
tests"` against `\b(crap|...)\b` proves only "doesn't fire on unrelated prose." `"the refactor is crappy but
ships cleanly"` proves the right-side `\b` correctly rejects `"crappy"` (word char follows) and that
`"ships"` isn't confused with `\bshit\b`. Far-miss bystanders are vacuous for selectivity.

For **rearrangement-preserving operations** (swap passes, stable sorts, permutation-preserving transforms),
the bystander invariant is *set/multiset equality*, not element-identity. Pre-seed input → Counter-of-codes →
apply op → Counter-of-codes must match across the complement of the targeted subset. Asserting
element-by-element equality on the complement fails spuriously because the op is *allowed* to rearrange there.
Target-only + strict-complement = false red; target-only + multiset-complement = correct.

## Time-dependent expected values

Tests whose expected values depend on `date.today()` (current month, current year, "days since X") MUST derive
them at runtime from the same formula the production code uses — never hardcode literals like `2026` or
`month 5`. Hardcoded date values silently rot: pass today, fail in six months with no warning, because the
assertion-path changes but the test still "succeeds" against a masked cell. If the derivation is non-trivial,
skip gracefully when the window is impossible (e.g. `current_month < 3`) rather than asserting against stale
ground truth.

## Bats files

Do not validate `.bats` files with `bash -n` — bats `@test` syntax is not standard bash and will always report
syntax errors. Use `bats` directly to run and validate.

**Path assertions:** under bats, `$HOME` resolves to a tmpdir inside `/tmp/`. Negative assertions like
`[[ "$path" != *"/tmp/"* ]]` false-positive even when production code is correct (the *expected* path also
lives under `/tmp/$HOME/...`). Assert the expected prefix instead (`[[ "$path" == "$HOME/.claude/..."* ]]`).

**A piped bats run masks the suite's exit code.** `bats … | tail -35` reports *`tail`'s* status (always 0), so a
red suite reads green and a test that never ran reads as passing. This is how a "does NOT kill" watchdog test
passed vacuously for a watchdog that was structurally incapable of killing anything — the negative assertion
holds trivially when the mechanism is dead. Capture `${PIPESTATUS[0]}`, or run unpiped and page the file.
Pairs with the general rule that a falsifier owes a demonstration it CAN go red.

**`rc=$?` after a `while read; do … done` loop reads the LOOP's status, not `read`'s** — and the loop's status
is 0 whenever the body succeeded. So a `>128` branch testing for a timeout/idle kill becomes dead code and the
guard silently degrades to a plain `wait`. Capture the status *inside* the loop at the `read` itself.

**Asserting on a hook's JSON stdout:** a Python hook emitting via `json.dumps(...)` (default
`ensure_ascii=True`) escapes every non-ASCII char — em-dash `—`→`—`, arrow `→`→`→`. So an
`assert_output --partial` substring spanning one of those glyphs never matches the raw output (it holds the
escape, not the glyph) and fails against a *correct* hook. Pick an ASCII-only span of the message
(`"keep going normally"`, not `"stop — keep going"`).

**Git hooks under test:** git ignores a `post-commit` exit status, so `assert_success` on `git commit` can never
fail — re-run the hook directly and assert on that. Commit hooks export `GIT_INDEX_FILE`; `unset $(git rev-parse --local-env-vars)` before running git in another repo.

## Python red demo — restore leaves a stale .pyc

A same-size mutate→restore inside one second keeps the mutated `__pycache__` (pyc checks mtime-seconds + size), so the next run tests the mutant: `rm -rf <pkg>/__pycache__` after every Python red demo.
